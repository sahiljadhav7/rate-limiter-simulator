# Working on Ratescale with an AI assistant

Ratescale is a rate-limiting simulator for students: the same seeded traffic runs through different rate limiters side by side, the load goes up until something breaks, and the app says what broke, why, and how to fix it. The plan and tickets are in `BaseConcept.md`; domain terms (Request, Attempt, Variant, Demand, Goodput, Finding) are defined in `CONTEXT.md`, and code, tests and UI text use those words.

## The one rule

**The numbers have to be true.**

Students learn from this. If fixed window lets through twice its limit, that has to be because the simulation admitted real Attempts across a real window edge and counted them, not because a chart was drawn to look right.

In practice:

- Every metric is measured from simulated events. Percentiles come from recorded latencies, never from a mean times a constant.
- A metric with no meaningful value for a Variant shows a dash or nothing, never a plausible-looking number.
- Runs are **deterministic**: the same seed and control timeline replay the exact same run. The only clock is the simulated clock and the only randomness is the seeded RNG streams.
- Work is finished when a script or test prints real output that shows the behaviour. "Should work" is not finished.

## Layout

```
src/sim/      the engine: event loop, traffic, limiters, backend, metrics, diagnoser. Pure TypeScript
src/runner/   builds one engine per Variant, advances them in lockstep, enforces the event budget
src/ui/       React: panels, charts, controls, diagnosis card
tests/        invariants, limiters, queueing theory, diagnosis
```

`src/sim` knows nothing about the UI: no React, no DOM, no timers, no global state. That boundary is what makes it testable and lets it move into a Web Worker later, so keep it.

## Commands

Scripts are in `package.json`. Run tests with `bun run test`, which is Vitest; plain `bun test` starts Bun's own test runner and finds nothing useful.

## Things that will bite you

**Determinism breaks quietly.** A single `Date.now()` or `Math.random()` inside `src/sim` makes replays drift with no error. Traffic, service times and retry jitter each draw from their own RNG stream, so an extra draw in one never shifts the others. Events with equal timestamps pop in insertion order via the sequence number.

**Traffic is generated by simulated time, not by frame.** The shared traffic source generates arrivals exactly up to `untilMs`, and control events apply before generation. Generating ahead per frame makes replays depend on frame timing.

**Per-second buckets hide the boundary burst.** A burst straddling the window edge splits across two one-second buckets and each looks like 1x the limit. The boundary-burst chart plots allowed Attempts in the last window, sampled every tenth of a window.

**Abandoned work still runs.** A timed-out Attempt keeps its Backend slot until service ends; its late response is discarded and counted as Wasted Work. That is what makes goodput collapse possible, so it is intended, not a leak.

**A backgrounded browser tab suspends `requestAnimationFrame`.** The simulation stalls and reads zero everywhere. Check `document.visibilityState` before diagnosing anything.

**Hard-reload before concluding something is broken.** A stale HMR module can survive a code change.

**Per-kind colours are a specificity trap.** A class selector and an attribute selector such as `[data-kind='limiter']` have equal specificity, so source order decides. Declare `--k-*` tokens only on the kind attribute rule, and put fallbacks inside `var()`.

## Statistical tests

Every statistical test uses a fixed seed, a run long enough to settle, and an explicit tolerance band (for example, Poisson mean within 3 percent over 60 simulated seconds). A test that passes on some seeds and fails on others is a bug in the test.

## Adding a limiter algorithm

1. Add the name to `LimiterSpec.algo` and document any new config fields with meaning and units
2. Implement `Limiter.decide(clientId, now)`, using only the `now` it is given
3. Support both `keyBy` scopes: global and per client
4. Write that algorithm's own "never exceeds" invariant (token bucket allows bursts up to capacity; leaky bucket delays rather than rejects)
5. A test proving it behaves differently from every existing algorithm on the same traffic

Step 5 is the real bar. An algorithm that matches an existing one on every scenario teaches nothing; that is why leaky bucket is a queue (`docs/adr/0001-leaky-bucket-as-queue.md`).

## Adding a scenario

- One lesson each, and the explainer says what to watch
- The lesson is visible at default settings, in the Variant it is about
- Stable at the default Demand, and degrades visibly at 2 to 4x
- A "what this models and what it leaves out" note
- A row in the diagnosis table test listing the Findings it produces and which is the Root Cause

Do the arithmetic first: the Backend's ceiling is `slots * (1000 / meanMs)` requests per second.

## Adding a diagnosis rule

- Thresholds are named constants with a doc comment saying what they measure and why that value
- One fixture that triggers it and one healthy fixture
- Update the scenario Findings table, since a new rule can fire in scenarios written for other rules

## Writing

The reader is a student who has not taken a queueing theory course.

- Plain language. "Requests waiting for a slot" beats `queueDepth`.
- Sentence case. Spell out abbreviations on first use.
- Say why something matters, not only what it is.
- Use commas, semicolons or a second sentence where you might reach for an em dash.

## Design

Visual language, tokens, layout and chart rules are in `DESIGN.md`; follow it for anything under `src/ui/`. The short version:

- Flat surfaces with borders and soft shadows. Colour carries meaning only: a kind's colour identifies it, status colours mean trouble.
- Every colour comes from a token in `src/ui/tokens.css`.
- Numbers in the mono stack with tabular figures.
- Interface transitions take 120 to 200 ms, and `prefers-reduced-motion` turns them off.
- Text meets WCAG AA. Compute the contrast ratio.

## Working autonomously

- Verify before reporting. "I ran the retry-storm scenario and Retry Amplification reached 2.4x" beats "this should work".
- Say what you did not check. An honest gap costs less than a confident report on unverified work.
- Leave commits to the human.
- One logical change at a time.
